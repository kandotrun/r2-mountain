# S3 Mountain フェーズ1設計

作成日：2026-11-04（Asia/Tokyo）

この文書は、承認済みのメニューバー版の設計を実装可能な仕様にまとめたものである。
最初の接続検証対象は、後から指定された標準管轄の `drive` バケットとする。
Account ID と認証情報は、この文書や Git に保存しない。
コードとアプリの動作は、まだ検証していない。
実装順序と検証方法は[実装計画](../plans/2026-11-04-s3-mountain-phase1-implementation.md)に記載する。

## 1. 目的と対象

Cloudflare R2 の1バケットに、数GBから数十GBのファイルを Mac からアップロードする。
メニューバーの画面にファイルやフォルダを渡すと転送が始まり、回線断やアプリ終了の後も、完了済みのパートを使って再開できる。

利用対象は Kan 自身の Mac とする。
フェーズ1はアップロードを先に使えるようにし、フェーズ2で File Provider による Finder 連携、閲覧、ダウンロード、削除を追加する。
Finder 上での直接編集やフォルダ移動は今回の対象に含めない。

## 3. 構成と責務

```text
s3-mountain/
  Packages/MountainCore/
    Package.swift
    Sources/MountainCore/
      S3/                 HTTP、SigV4、R2 API、XML
      Upload/             分割、転送、再試行、状態遷移
      Persistence/        ジャーナル、キューの復元
    Tests/MountainCoreTests/
  App/                    SwiftUI、Keychain、通知、スリープ抑止
  project.yml             XcodeGen のプロジェクト定義
  justfile                ビルドと検証の入口
  docs/superpowers/
```

`MountainCore` は SwiftPM のライブラリとし、SwiftUI、AppKit、File Provider に依存させない。
S3 通信には URLSession、署名とダイジェストには CryptoKit を使う。
外部の実行ファイル、FUSE、外部 Swift パッケージを必要としない。

自作クライアントは、必要な API と送信形式を小さく制御するための選択である。
AWS SDK 全般が R2 で利用できないという前提は置かない。
R2 が受け付ける形式を、通信層の契約テストで確認する。

通信、時刻、再試行の待機、ファイル読取り、ジャーナル保存を差し替え可能にする。
エンジンは actor とし、ファイルは1つずつ、1ファイル内のパートは最大4本並列で処理する。
UI には `AsyncStream` などの購読可能な状態スナップショットを渡す。
画面を閉じてもエンジンは停止しない。

## 4. 入力ファイルと保存先

メニューバー画面はファイルとフォルダのドロップ、および選択ダイアログを受け付ける。
ファイル単体はその名前、フォルダはトップのフォルダ名を含む相対パスを保持する。
例えば `素材/撮影/動画.mov` を渡し、プレフィックスが `backup/` なら、キーは `backup/素材/撮影/動画.mov` となる。

キーは各パス要素を NFC に正規化して組み立て、S3 用の UTF-8 パーセントエンコードは通信層だけで行う。
空白、`+`、`%`、日本語、連続する `/` の扱いをテストし、二重エンコードを避ける。
プレフィックス内の `.` と `..` は受け付けない。
空フォルダ用のオブジェクトは作らない。
シンボリックリンクと特殊ファイルは辿らず、スキップした項目を画面に表示する。
フォルダを渡した場合の `.DS_Store` と `._*` は転送から除外し、それ以外の通常の隠しファイルは含める。

投入時に接続プロファイル、プレフィックス、相対パス、元ファイルの識別情報を固定する。
後の設定変更を待機中の項目へ自動適用しない。
同じファイルの重複投入や、NFC 正規化後に同じキーになる項目も衝突判定の対象にする。

### 同名ファイルの保護

既存キーがあれば `名前 2.ext`、`名前 3.ext` の順で候補を選ぶ。
キュー内でもキーを予約し、同じ保存先を並列に選ばない。
`HEAD` の404だけを未存在とみなし、403や通信失敗を未存在として処理しない。

小さいファイルの `PutObject` には `If-None-Match: *` を付ける。
競合した場合は新しい名前を選んで再試行する。
R2 はこの条件付き PUT を文書化している。[R2 の条件付き PUT](https://developers.cloudflare.com/r2/api/s3/extensions/#conditional-operations-in-putobject)

マルチパートでは、`HEAD` の確認後から完了までに別の書き込みが入る場合も考慮する。
`CompleteMultipartUpload` の `If-None-Match: *` は、R2 の公式互換表だけでは対応を確定できない。
実 R2 で「既存オブジェクトを保持したまま条件付き完了が失敗すること」を確認するまで、競合時にも上書きしない保証を満たしたとは扱わない。
無条件の完了処理に切り替えてこの検証を省略しない。
未対応の場合は、重複を避けるキー方式などの設計を解決してから大容量転送を利用可能にする。
これはフェーズ1の実装初期に判定する項目である。[S3 API 互換表](https://developers.cloudflare.com/r2/api/s3/api/)

条件付き完了が利用できる場合でも、競合で完了を拒否されたマルチパートを別キーへ移すことはできない。
新しい連番を選び、既知の旧 upload ID を片付けて、新しいキーへ最初から転送する。
通信エラーで結果が不明な場合は、競合確定として名前を変える前に、後述の結果照合を行う。

## 5. R2 への転送

### 接続と署名

標準の接続先は `https://<account-id>.r2.cloudflarestorage.com`、EU 管轄は `https://<account-id>.eu.r2.cloudflarestorage.com` とする。
AWS Signature Version 4 の region は `auto`、service は `s3` とし、バケットを含む path-style URL を使う。
接続先ホストは Account ID と管轄から生成し、任意ホストへのリダイレクトで署名情報を送らない。[R2 S3 API](https://developers.cloudflare.com/r2/api/s3/api/)

必要な API は `ListObjectsV2`、`HeadObject`、`PutObject`、`CreateMultipartUpload`、`UploadPart`、`ListParts`、`CompleteMultipartUpload`、`AbortMultipartUpload` とする。
接続テストは対象バケットで少数のオブジェクトを列挙し、アカウント全体のバケット一覧権限を要求しない。

送信本文は長さが確定したデータかファイル範囲から作る。
本文があるリクエストには正しい `Content-Length` を付け、`aws-chunked` やストリーミング署名を使わない。
S3 のペイロード署名には `UNSIGNED-PAYLOAD` を用い、TLS で送信する。
単一 PUT と各パートには Base64 の `Content-MD5` を付ける。
`x-amz-content-sha256` にも `UNSIGNED-PAYLOAD` を設定し、`Content-MD5` と送信する `x-amz-*` メタデータを署名対象に含める。
URLSession が実際に送ったヘッダーと本文も、ローカル受信サーバーおよび実 R2 で確認する。
この固定長の送信方針はアプリの通信契約であり、すべてのストリーミング方式が R2 で非対応だと一般化しない。[Cloudflare SDK 設定例](https://developers.cloudflare.com/r2/examples/aws/aws-sdk-net/)

署名の canonical path と query は、送信 URL と同じエンコード結果から作る。
空の `uploads` 値、`uploadId`、XML 内の特殊文字、ETag の引用符を保持する。
XML パーサーは外部エンティティを解決せず、HTTP ステータスと S3 のエラーコードを分けて扱う。

### 分割とメモリ

64 MiB 未満は単一 PUT、64 MiB 以上はマルチパートとする。
0バイトのファイルは単一 PUT で扱う。
MiB は `1,048,576` バイトである。

ファイルサイズを `S` としたパートサイズは、整数演算で次のように決める。

```text
partSize = roundUpToMiB(max(64 MiB, ceil(S / 10_000)))
partCount = ceil(S / partSize)
```

全パートを同じサイズに揃え、最後のパートだけ短くしてよい。
10,000パート以内、R2 のパートサイズとオブジェクトサイズの上限以内であることを、送信開始前に確認する。
50 GiB なら64 MiBの800パートになる。[R2 multipart](https://developers.cloudflare.com/r2/objects/upload-objects/#multipart-upload)、[R2 limits](https://developers.cloudflare.com/r2/platform/limits/)

2026-11-04に確認した制限ページでは、本文の概数と脚注の厳密値に差がある。
実装の検査は脚注の小さい値を採用し、オブジェクトは `5 TiB - 5 GiB` 以下、各リクエストの本文は `5 GiB - 5 MiB` 以下、非最終パートは5 MiB以上とする。
制限定数には参照元と確認日を残す。[R2 制限の脚注](https://developers.cloudflare.com/r2/platform/limits/#footnotes)

数十GBのファイル全体をメモリへ読み込まない。
4本の64 MiBパートでは、ペイロードだけで約256 MiBになるため、実測では URLSession の複製なども含めて確認する。
大きいパートにもメモリ使用量が比例し続けないよう、ファイル範囲から一時ファイルへ切り出す `PartSource` を用意し、同時保持量を制限する。
一時ファイルはキャッシュ内に作り、読取りと MD5 計算をまとめて行う。
空き容量が足りない場合は元ファイルを保持したまま停止する。

## 6. ジャーナルと途中再開

アップロードごとの JSON とキューの索引を Application Support の専用ディレクトリに保存する。
保存ディレクトリは所有者だけが読める権限、JSON は所有者だけが読み書きできる権限にする。
JSON にはスキーマバージョン、ジョブID、固定した接続先、元ファイルのURLと識別情報、キー、ファイルサイズ、パートサイズ、upload ID、状態、完了済みパートを保存する。
各パートは番号、長さ、ETag、送信時の MD5 を持つ。
Secret Access Key、Authorization ヘッダー、署名済み URL は保存しない。

状態更新は一時ファイルへの書込みと原子的な置換で行う。
upload ID の保存が成功するまでパート送信を始めず、各パートの成功直後にジャーナルを更新する。
単一 PUT の直前には `putPending`、完了要求の直前には `completing` と、固定キー、ジョブID、期待サイズ、期待 MD5 または ETag を保存する。
この保存に失敗した場合は送信しない。
再起動でこの状態を復元した場合は、最初に送信結果を照会する。
同じジョブの成功直後にアプリが落ちた場合も、412を別ファイルとの衝突と見なして改名する前に自分の完了を確認する。
保存失敗後も転送だけを進めることはしない。
プロセスの強制終了からの復元を対象とし、ストレージ自体の故障や電源断からの完全復旧までを保証しない。

再開は次の順で行う。

1. ジャーナルを読み、接続プロファイルと元ファイルが利用できることを確認する。
2. ファイル識別子、サイズ、更新時刻を投入時の値と照合する。
3. upload ID があれば `ListParts` を全ページ取得する。
4. ローカルと R2 でパート番号、サイズ、ETag が一致するパートを再利用する。
5. R2 にだけあるパート、ローカルにだけあるパート、値が異なるパートは、同じ番号で元ファイルから再送する。
6. 全パートを番号順に並べ、元ファイルを再確認してから完了を要求する。
7. 完了結果と `HeadObject` のサイズ、期待する multipart ETag、ジョブIDのメタデータを照合して完了を保存する。

ETag を常にファイル全体の MD5 と見なさない。
`ListParts` は最大1,000件ずつ取得し、`IsTruncated` と `NextPartNumberMarker` に従ってページングする。
マーカーの欠落と前進しないページをエラーにする。
R2 の multipart ETag は、各パートのバイナリ MD5 を連結して再び MD5 を計算し、パート数を付けた値として検証する。
パート番号の上書きが失敗すると以前のパートを失う場合があるため、結果が不明な再送後は再び照合する。[AWS ListParts](https://docs.aws.amazon.com/AmazonS3/latest/API/API_ListParts.html)、[R2 ETags](https://developers.cloudflare.com/r2/objects/upload-objects/#etags)、[R2 UploadPart](https://developers.cloudflare.com/r2/api/s3/api/#behaviors--limitations)

リクエストがサーバーで成功し、応答だけ失われる場合も扱う。
`CreateMultipartUpload` の応答喪失で upload ID を取得できなければ、未知の upload ID を推測して中止しない。
アプリが記録した upload ID だけを明示的な中止処理の対象とし、残った未知のアップロードはバケットのライフサイクルに委ねる。

単一 PUT とマルチパートの作成時に `x-amz-meta-s3-mountain-job-id` を設定する。
PUT または完了要求の応答が失われた場合は、同じキーを `HeadObject` で照会する。
サイズ、ジョブID、期待する ETag が一致すれば完了として回収し、他のジョブのオブジェクトを自分の成功として扱わない。
HTTP 200でも本文に S3 エラーがあれば成功としない。[AWS CompleteMultipartUpload](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CompleteMultipartUpload.html)

完了の XML が途切れた場合や応答が失われた場合は `reconciling` に移り、ジャーナルを保持する。
進行中の書込みに対する `HEAD` の404は、書込み失敗の証拠にはしない。
新しい名前で二重転送する前に、進行中の通信の終了と既存キー、upload ID の照合を行う。
成功とも失敗とも確定できなければ、結果確認待ちとして利用者に表示する。[R2 の書込み中の読取り](https://developers.cloudflare.com/r2/reference/consistency/#negative-reads-and-in-flight-writes)

`NoSuchUpload` の場合も、先に完了済みオブジェクトを照会する。
PUT または完了要求を送った可能性がある場合は、前述の結果確認待ちの規則を優先する。
未確定の書込みが残っておらず、自分の完了がないと確定でき、元ファイルが変わっていなければ、新しい upload ID で最初から送る。
R2 の未完了アップロードの自動破棄は、標準設定では開始から7日後であり、バケットの設定で変更できる。
7日間無通信だったかどうかを再開可否の判定に使わない。[R2 lifecycle](https://developers.cloudflare.com/r2/buckets/object-lifecycles/)

元ファイルは各読取りの前後と完了直前に再確認する。
変更を検出した場合は完了を要求せず、記録済みのマルチパートを中止する。
サイズと更新時刻の照合は通常の変更検知であり、同じメタデータを保つ改変まで検出する保証ではない。
単一 PUT は、検査済みの一時ファイルから送って本文を固定する。

## 7. 状態とエラー処理

| 状態 | 表示と操作 |
| --- | --- |
| `queued` | 順番待ち。キャンセルできる |
| `uploading` | 転送量、速度、残り時間を表示。一時停止とキャンセルができる |
| `putPending` / `completing` | 本文固定後のPUTまたは完了処理中。送信意図を保存済み |
| `reconciling` | 応答が失われた転送の結果を照会する。キーを変えて二重転送しない |
| `paused` | ユーザーが停止。明示的な再開まで保持する |
| `waitingForNetwork` | 回線または再試行時刻を待つ。手動再開もできる |
| `needsCredentials` | 設定を直して接続テスト後に再開する |
| `failed` | 理由と対処を表示。元ファイルの変更などを無条件に自動再試行しない |
| `cancelling` | 通信を止め、既知のマルチパートの中止を処理する |
| `cancelled` | 中止完了。元ファイルを保持する |
| `completed` | 保存先キーをコピーできる |

通信断、タイムアウト、429、再試行可能な5xxには、上限つきの指数バックオフと jitter を使う。
`Retry-After` があれば尊重し、無制限にリクエストを送り続けない。
自動再試行を使い切ったら待機状態にし、到達性の回復または上限つきの待機タイマーで再試行する。
NWPathMonitor の変化だけに依存すると5xx後に再開できないため、手動再開も常に残す。

認証と権限のエラーは設定修正待ちにする。
時刻ずれを表す S3 エラーでは、期待する HTTPS 接続先の Date から一時的な署名時刻の補正を作り、回数を制限して再署名する。
Mac の時計をアプリが変更することはない。

一時停止では、進行中の通信をキャンセルしてタスクの終了を待ち、成功応答を受けたパートを保存する。
その後は新しいパートと完了要求を送らない。
完了要求や単一 PUT がすでに送られていた場合は、結果を照合してから停止状態を確定する。
この間に完成したオブジェクトは、キャンセル操作を理由に自動削除しない。
キャンセルでは、既知の upload ID にだけ `AbortMultipartUpload` を送る。
オフラインで中止できなければ `cancelling` と中止待ちの記録を残し、次回の通信回復後に処理する。
別ツールが作ったオブジェクトや未完了アップロードを一括削除しない。

起動時は転送中だった項目を復元し、照合して再開する。
ユーザーが一時停止した項目は自動再開しない。
破損した JSON は隔離し、他の項目の復元を継続する。
将来のスキーマを検出した場合は破棄せず、更新が必要なことを表示する。
同じジャーナルを複数プロセスが処理しないよう、アプリを単一起動にする。

## 8. 画面と認証情報

メニューバー画面には、バケット名、編集可能な宛先プレフィックス、ドロップ領域、ファイル選択、転送キュー、設定、終了を置く。
キューはファイル名、保存先キー、状態、送信済み量、速度、残り時間と状態に応じた操作を表示する。
速度と残り時間は推定値とし、再開時の完了済み量から速度を算出しない。
失敗時は認証、通信、元ファイル、ローカル保存のどこを直すかが分かる日本語を表示する。

設定画面は Account ID、Access Key ID、Secret Access Key、バケット、管轄（標準またはEU）、接続テストを持つ。
Secret は Keychain に保存し、入力欄とログでは秘匿する。
保存済みの Secret は画面へそのまま再表示しない。
認証情報は実装やテストに埋め込まず、バケットに限定した Object Read & Write 権限を利用する。[R2 API tokens](https://developers.cloudflare.com/r2/api/tokens/)

転送中だけスリープ抑止を取得し、待機、一時停止、完了、失敗で解放する。
ユーザーによる明示的なスリープまでは阻止しない。
通知権限は利用時に求め、拒否されてもキュー内で結果を確認できる。
処理中の終了には、次回起動で再開できることを示す確認を出し、通信終了とジャーナル保存後に終了する。

## 9. 検証と利用可能の条件

`swift test` を中心に、失敗するテスト、最小実装、整理の順で開発する。
SigV4 は AWS の公開例で既知の署名と比較する。
偽の S3 と通信記録用 transport で、分割、並列数、再試行、ファイル変更、中止、応答喪失、強制終了後の再開を検証する。
`swift format` を lint の入口とし、`just` に実行手順をまとめる。

実 R2 テストは明示的に起動し、認証情報を与えた場合だけ実行する。
ランダムな専用テストプレフィックスを使い、生成したキーと upload ID だけを片付ける。
削除権限はテスト後の片付けにだけ必要であり、通常のアップロードに削除処理を混ぜない。

フェーズ1を利用可能とするには、次をすべて確認する。

- 条件付き PUT と条件付きマルチパート完了の競合保護が実 R2 で確認できるか、未対応時の保存先設計が解決している。
- 150 MiB以上のテストファイルを送信し、ダウンロードした内容の SHA-256 が元と一致する。
- アプリを途中で強制終了し、起動後に完了済みパートを再利用して転送できる。
- 数十GBのファイルでも、ファイルサイズに比例してメモリを消費しない。
- 回線断、認証失敗、元ファイル変更、一時停止、キャンセルが、それぞれ指定した状態になる。
- 日本語名、フォルダ、0バイト、同名、NFC 衝突で保存先と内容が正しい。
- 選択した個人チームで署名されたアプリが、この Mac で起動できる。
- Finder からのドロップ、Keychain 保存、通知、終了と再開を実際の画面で確認できる。

単体テスト、ビルド、署名、GUI、実 R2 は、それぞれ結果を分けて報告する。
仕様書の完成だけで、アプリや大容量転送が完成したとは扱わない。
